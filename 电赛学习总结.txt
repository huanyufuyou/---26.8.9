1.2 一份电控手的"三层认知"
--------------------------------------------------

写这份总结前，笔者重新翻了这一年的代码，最大的体会是：编程的很多道理是相通的。

  · 多级菜单的起源是数据结构里的链表——菜单项一个个串起来，前后跳转就是节点遍历；
  · 笔者后来了解到的 FreeRTOS，其任务间通信又和队列息息相关；
  · 状态机本质上是离散逻辑的图。

如果你有数据结构的基础，会发现这些"工程技巧"都不是新东西，只是换了个皮。
反过来，如果只背数据结构而不做工程，你也永远不会意识到链表能用来做菜单。

由此笔者给自己总结了"电控手的三层认知"，也是这份文档贯穿始终的一条线：

  1. 编程眼界——数据结构与算法、代码组织。决定你的代码能不能撑住复杂度。
  2. 数学原理——控制算法背后的数学（PID 就是高等数学里微分、积分的直接应用）。
                决定你是"会调参"还是"懂控制"。
  3. 底层实现——时序、时间片调度、寄存器与中断。决定出了问题你知不知道去哪查。

三层缺一不可：没有编程眼界，功能能做出来但代码烂到不敢改；没有数学原理，
参数只能靠蒙；没有底层认知，程序死机了都不知道是被哪个中断抢死的。

二、任务架构（核心）
==================================================

这一部分是全文的重心。做复杂工程，代码组织比算法更重要。

--------------------------------------------------
2.1 状态机：可以暂时不用，但不能不会
--------------------------------------------------

很多时候，对于较简单的工程逻辑，诸如"是否丢线？"亦或"是否接收到有效信息？"，简单的 if-else 语句便能解决问题。但面对一个复杂的逻辑要求——如何让小车从弯道变直道、直线变丢线、弯道碰到十字路口时及时切换不同应对状态——情况就不一样了。

不同情况下的状态转变，若仍沿用 if-else 的写法，意味着大量的嵌套；而一旦更新其他状态，整体都要再次大改，可调试性和可读性大幅降低。一个良好的状态机写法则不仅清晰明了，还降低了代码的编写量。

状态机基于 switch-case 写法，切换靠事件，而非一堆互相咬合的 if。如此一来，小车从"我该怎么判断这个有一堆条件的任务并执行"，变成了"我处于什么状态就做什么状态该做的事"——从一个交错的树，变成了可查状态指令的表。

以循迹小车为例，状态机大致是这样的：

  状态：直道 / 弯道 / 丢线 / 十字路口
  切换：
    直道 ----------------持续单侧偏离--------------> 弯道
    直道 --持续稳定小误差（允许偶尔单侧偏移）----> 直道
    弯道 ----------------全丢线-------------------> 丢线
    弯道 ----------------检测十字------> 十字路口特殊处理
    丢线 -----------------重见线-------------------> 直道

每个状态的处理是独立的，互不干扰；新增一个状态，只需要加一个 case 和它的事件来源，旧代码不用动。

实际上，对于状态机的使用，笔者用得并不深——弯道直道判断只是它最浅的一层用法。状态机真正的威力在于复杂任务的编排：路口决策、多任务切换、异常恢复，那是笔者还没真正触及的，也是未来的设想。但为什么值得把它写进来？因为可以暂时不用，但不能不会——当逻辑复杂到 if-else 已经撑不住的时候，再回头学，成本就高了。

--------------------------------------------------
2.2 时间片轮询：裸机下的轻量调度
--------------------------------------------------

状态机解决的是"逻辑怎么组织"，这一节解决的是"任务怎么运行"。

对于刚学完单片机的大部分学生，都喜欢采用裸延时——所有任务都塞在主函数里，一个做完做下一个。而屏幕刷新要延时等回复，按键消抖要延时，走脉冲要延时——如果这些都写成 delay，一个任务的延时会把其他所有任务卡死，并且任务越多，一旦某一个任务执行时间过长，就会导致后续任务全都阻塞。于是有同学会把延时全放入中断：按键中断、串口中断、定时器再开几个。中断确实不阻塞了，但代价是新问题——中断里不能做长事（要短、要快），而且中断之间还有优先级冲突，一个慢中断会阻塞一个快中断。功能一多，中断表也就变得复杂而难以调试。

时间片轮询是介于两者之间的一条路：慢的、会阻塞的工作留在主循环里轮询；快的、对时间敏感的工作，在 1ms 节拍中断里只做"登记"。核心思想是——中断只负责"到点提醒"，实际干活全在主循环。

实现很朴素，四个要素：

  1. 一张任务表：每个任务登记函数指针、运行周期、运行计时器；
  2. 一个 1ms 节拍中断：给所有任务的计时器加一，到点的把运行标志置位，仅此而已；
  3. 一个主循环：死循环轮询任务表，谁标志被置位就执行谁，执行完清标志；
  4. 两个操作接口：立即唤醒（GetUp）、立即休眠（Sleep），用于事件驱动——
     比如某任务被串口指令唤醒，或某任务忙完自己睡下。

节拍中断的真实实现，短得没有秘密：

  void OS_ClockInterruptHandle(void) {
    for (i = 0; i < OS_TASK_SUM; i++) {
      if (OS_Task[i].task != 0) {
        OS_Task[i].RunTimer++;
        if (OS_Task[i].RunTimer >= OS_Task[i].RunPeriod) {
          OS_Task[i].RunTimer = 0;
          OS_Task[i].RunFlag = OS_RUN;   /* 只置标志，不做事 */
        }
      }
    }
  }

主循环的调度，一样朴素：

  while (1) {
    for (i = 0; i < OS_TASK_SUM; i++) {
      if (OS_Task[i].RunFlag == OS_RUN) {
        OS_Task[i].RunFlag = OS_SLEEP;   /* 先清标志，再执行 */
        (*OS_Task[i].task)();
      }
    }
  }

代码只有几十行，但每条规则都是"设计"出来的：

  · 中断里只置标志：中断上下文要求快而短，把"做事"留给主循环，实时性由周期保证，
    而不是由中断长度保证；
  · 先清标志再执行：防止任务还没跑完，下一次节拍又把它置起来，造成重入；
  · 标志位必须 volatile：中断与主循环共享的变量，不加 volatile，编译器优化后可能读旧值；
  · GetUp / Sleep 要关总中断：任务表是共享资源，中断随时可能改写标志，
    操作它时先关中断再开，保证原子性。

H 题的注册表更能说明问题（10ms 节拍，周期按节拍数登记）：

  OS_CreatTask(OS_TASK1, OS_Task1_DutyProc, 1, OS_RUN);  /* 电赛状态机 10ms：灰度/IMU/编码器融合 */
  OS_CreatTask(OS_TASK2, AppProc,            5, OS_RUN);  /* OLED/菜单 50ms：整屏 I2C 重绘 20~30ms */
  OS_CreatTask(OS_TASK3, Hal_YawUart_Proc,   2, OS_RUN);  /* yaw 串口 20ms（50Hz） */

OLED 整屏 I2C 重绘一次要占用20~30ms，如果在裸循环里跑，或者用延时等待，会导致其他任务阻塞。时间片的做法是
给予50ms 的时间片，运动控制照样 10ms 一个节拍，相不干扰。

周期怎么定，有规律可循：凡是运动控制、状态机扫描这类要跟物理世界同步的任务，取 10ms
甚至更短；凡是屏幕绘制这类一次重绘就要吃掉大量时间片的任务，用单独的慢周期，避免短时任务的路。慢任务占用少，快任务才有时间片。

协作式调度的代价也要知道：一个任务跑太久，会堵住后面所有任务。所以规则是——任务函数里不放延时循环，不等待阻塞，每个任务在"自己这个周期里做完一次该做的事"就返回；做不完，就拆成两步。

但朴素也有不足，这套调度器没有优先级，没有抢占，谁先谁后全看注册顺序。但正因为它朴素，才让人敢往上叠功能：加一个任务只是表里多一行，不碰任何旧代码。笔者后来了解到 FreeRTOS 时才恍然——自己手工搭的这套东西，其实已经摸到了操作系统的门把手。

从时间片轮询到 FreeRTOS
~~~~~~~~~~~~~~~~~~~~~~~~

FreeRTOS 不是新东西，它是这套手工调度的工业级升级，概念几乎一一对应：

  手工任务表        →  FreeRTOS 任务（Task）+ 就绪队列
  1ms 节拍          →  SysTick 系统节拍
  主循环轮询        →  调度器（空闲时跑空闲任务）
  标志位 + 关中断   →  信号量 / 互斥锁 / 临界区 API
  GetUp 事件唤醒    →  信号量 / 事件组 / 队列
  协作式（跑完才让）→  抢占式（高优先级随时插队）
  共享全局变量传参  →  消息队列（数据流解耦）

手工调度解决了"轮着跑"，FreeRTOS 额外解决了三件事：一是优先级抢占——紧急的事可以打断不紧急的；二是阻塞等待——任务可以睡着等信号量、等队列，而不是空转轮询；三是层间解耦——层与层之间不直接调用，而是通过队列传消息，依赖方向被数据结构固化下来。

值得注意的是：FreeRTOS 的队列，本质上就是数据结构里的环形队列。多级菜单的根是链表，FreeRTOS 的根是队列——所谓新框架，不过是把学过的基础数据结构，用在实时系统的场景里。编程的很多道理，确实是相通的。

学 FreeRTOS 之前，如果没手写过调度器，你对"任务""优先级""临界区"这些词是没有体感的，它们只是文档里的名词。自己写过几十行调度器之后，再回头翻 FreeRTOS 的文档，每个概念都能在脑子里对应到一段真实的代码。把时间片轮询放在全文最前面的原因就在这里：它是通往操作系统的一座便宜的桥。

--------------------------------------------------
2.3 多层解耦任务框架：做复杂工程的利器
--------------------------------------------------

状态机管逻辑，时间片管调度，这一节管的是代码放在哪里、谁能调用谁。

不妨先看不分层的样子。很多同学刚写程序时，习惯把功能都塞进 main.c，读传感器、算逻辑、刷屏幕、控电机，从上到下一排写完。
顶多就是跟江科协一样，硬件全甩到hardware文件夹，调用的内容全放在user里。功能少的时候没什么问题，功能一多就撑不住了：换一个传感器型号或者单片机，要顺着所有调用点挨个改；屏幕显示和电机控制写在同一个文件里，改显示的人随时可能碰坏电机逻辑；代码膨胀到几千行之后，已经说不清每一行到底属于哪个功能。

分层的做法，是先把代码按"离硬件多远"切成几层，然后立一条规矩：上层可以调用下层，下层永远不能反向 include 上层。E 题工程里用的是五层：

  层级  名称      目录       职责
  L5  任务层     Duty/     任务编排、比赛状态机
  L4  应用层     App/      多级菜单、按键交互、界面显示
  L3  中间件层   Mt/       运动规划（Jog、位姿）、视觉处理
  L2  硬件抽象层 Hal/      步进电机、舵机、电磁铁、屏幕、串口的驱动接口
  L1  驱动层     bsp/board/ 寄存器初始化、OLED/按键/串口的底层驱动

依赖方向一旦定死，每一层的修改边界就清楚了。换一个电机驱动芯片，改的是 Hal 层及以下，Duty 里的任务逻辑一行不用动；要换主控 MCU，理论上重写 L1 和 L2，上层代码可以整体搬走。分层本质上是把"改动的影响范围"框死，让改动不扩散。

用 E 题里的一个真实场景，看一次需求怎么穿过这五层。在屏幕上按一个按键，让拼图模块执行一次搬运：

  L5 Duty：任务状态机收到"开始搬运"事件，进入搬运状态，往下发指令；
  L4 App：菜单响应按键，把"搬运"写进当前任务配置；
  L3 Mt：运动规划算出这次搬运要用到的各轴步数与速度；
  L2 Hal：调用步进电机的驱动接口，给定方向、脉冲数；
  L1 驱动：最终落成定时器产生的那一串脉冲。

每一层只做自己分内的事，层与层之间通过接口衔接，不靠全局变量互相咬合。这样做的直接回报是排查问题的路径变得很短：出问题了，先在 Duty 里看状态对不对，再看 Mt 给的参数对不对，再查 Hal 的接口有没有被调用——问题一定落在某一层的某个函数里，不会悬在半空。

分层也不是越细越好。任务简单时硬套五层，只会多出一堆没意义的跳转和文件。判断标准只有一个：这个工程还要不要继续加功能。只要还要加，分层就值得。

--------------------------------------------------
2.4 多级菜单：人机交互的起点
--------------------------------------------------

比赛现场没有上位机，参数调整、传感器校准、题目选择全靠那块屏幕加几个按键完成。多级菜单看似不起眼，却是整个工程人机交互的起点——菜单不顺，后面所有调试都是在受罪。

朴素的做法是把界面写进一个个函数，用一堆 if 判断当前按键该干什么。界面少时没问题，界面一多，按键处理和绘制逻辑纠缠在一起，加一个界面就要改一大片，改得不敢动。

菜单的抽象方式，是把"一个界面"看成三件事：进入时做什么、绘制时画什么、按键来了怎么响应。E 题里笔者用函数指针把这三个动作打包进一个结构体：

  typedef void (*page_enter_fn)(void);
  typedef void (*page_paint_fn)(void);
  typedef void (*page_key_fn)(key_event_t ev);

  typedef struct {
    page_enter_fn enter;    /* 进入页面 */
    page_paint_fn paint;    /* 绘制页面 */
    page_key_fn on_key;     /* 按键响应 */
  } menu_page_ops_t;

配合一个记录当前页的枚举，调度就变成"查当前页，调用它对应的三个函数"。加一个新页面，只是往页表里加一项，旧代码不用动。这和 2.1 的状态机是同一种思路：页面就是状态，按键就是事件。

菜单和数据结构的联系也在这里：菜单项一个个串起来、前后跳转，是链表上的节点遍历；一级套二级，是树的遍历。多级菜单不过是把数据结构课上的链表和树，用在了人机交互上。反过来，只背链表而不做工程，永远意识不到它能用来做菜单。

页面不算复杂时，也有轻量的写法。笔者H 题里用的是"一行一个选项的数组 + 选中行号 + 视口滚动"，配合 KEY1~KEY4 上下确认返回，几十行就能跑起来；等到每个页面都有各自的实时数据和按键语义，再升级成函数指针页。两种写法对应两种复杂度，和状态机"可以不用但不能不会"是同一个道理。

菜单还有两个容易踩的细节。一是绘制要带标记，内容没变就不重绘，否则菜单任务会白占时间片；二是实时数据页要降频，灰度值、yaw、PID 参数这类每秒都在变的页面，隔几拍刷一次屏就够了——整屏重绘要占不少时间，不能每个周期都刷。

==================================================
三、运动控制
==================================================

从这一部分开始，从"怎么把代码组织好"转到"怎么让车动得准"。

--------------------------------------------------
3.1 前馈 PID
--------------------------------------------------

先看纯反馈的问题。位置式 PID 里的比例项和积分项，都建立在"误差已经出现"的前提下：目标从 0 变成 30 cm/s，实际速度不可能立刻跟上，误差拉大，P 才发力，I 慢慢攒。整个过程里，控制量总是比目标慢半拍——误差小的时候输出也小，电机只能一点一点加速。纯反馈是"事后纠偏"，它不知道目标要变，只能等误差出来了才动。

前馈的思路不同：目标既然是我们自己定的，为什么不直接按目标算一份基准控制量先给上去，再让反馈去修剩下的偏差？速度环里就是这么做的：

  ff = (float)SPEED_FF * v_cmd;    /* 前馈项：直接把目标速度换算成 PWM */

SPEED_FF 是标定出来的换算系数（这个工程里是 90，单位 CCR 每 (cm/s)），意思是"想让车以 1cm/s 前进，电机该给多少 PWM"。它不需要很准，方向对、量级差不多就行，剩下的误差交给 PI 兜底：

  out = ff + ((float)SPEED_KP * e) + s_speed_i;   /* FF 扛主责，PI 只修偏差 */

这样目标一变，输出立刻跟上，不用等误差攒起来。所以速度环的 PI 都调得很弱——KP 只负责小偏差，I 更小，主力是前馈，反馈只是兜底。这正是 vehicle_tune.h 注释里那句"FF 扛主责，PI 只修偏差"的意思。

前馈系数从哪来？标定。让车以几个不同的固定速度跑，记下"目标速度 → 实际 PWM"的关系，拟合成一条直线，斜率就是 FF。这是 3.4 参数校准要讲的第一步。

--------------------------------------------------
3.2 PID 细节：死区 / 微分先行 / 积分饱和 / 变速积分
--------------------------------------------------

位置式 PID 的公式只有三行：P 看当下误差，I 攒历史误差，D 看误差变化趋势。公式简单，但真放到电机上调起来，四个坑几乎每个都会踩到。这一节把每个坑的症状、原因和解法分开讲。

死区。症状：车明明到位了，却在目标点附近来回小幅窜动；或者给了一个小 PWM，电机纹丝不动，只有嗡嗡声。原因有两个：传感器噪声，和电机静摩擦。误差小到一定范围时，控制量不足以克服摩擦，误差又消不掉，P 就一直小幅度输出，形成抖动；而小 PWM 输出根本推不动电机，纯属浪费。解法分三层：
- 误差死区：误差绝对值小于门限，直接当成 0 处理。速度环里 SPEED_ERR_DEAD=0.2，即 ABS(e)<0.2 时 e=0；
- 滞回死区：位置环防抖的关键。进入门限严、离开门限宽（位置 1.5cm 进、3cm 出；yaw 3 度进、6 度出），避免在边界上反复切换——只设一个门限的话，到位瞬间误差在门限附近抖动，状态会不停地进进出出；
- PWM 死区：小 PWM 电机不动，直接给 0。旧版代码里则是反向操作——输出加一个 Offset 偏置，让控制量一次性跨过静摩擦区。

微分先行。症状：目标值一变，输出先猛地冲一下，也就是微分尖峰。原因：微分作用在误差上，而目标阶跃的瞬间，误差本身就是一次突变，D 项把这次突变当成了真实变化率，放大出一个巨大的输出。解法是微分先行：对实际值微分，而不是对误差微分，D 项只反映实际值的变化率，目标突变进不了微分项：

  Diff = -pid->Kd * (pid->Actual - pid->Actual_Last);   /* 对实际值微分 */

代价是目标变化时 D 不会立即响应，但换来的是系统不再被自己的指令吓到。

积分饱和。症状：误差长时间很大，积分一路攒到上限；等目标反向后，积分要花很长时间才能退回来，导致严重的超调和振荡。原因就是积分项没有上限。解法有两项：
- 积分限幅：把误差积分夹在上下限之间（速度环 I_MAX=400）；
- 条件积分：输出已经顶满、且误差与积分同号时，撤销本次累加——既然积分已经让输出顶死了，再往里加只会让退出更慢。

变速积分。这是学 PID 时在江协科技教程里看到的做法，思想是：积分速度应该随误差大小变化。误差大时，系统还没跟上，积分要慢一点，避免攒过头；误差小时，再加快积分消除静差。实现是给积分乘一个系数 C，C 与误差绝对值成反比：

  float C = 1 / (0.2 * fabs(Error0) + 1);    /* 误差越大，C 越小，积分越慢 */
  ErrorInt += C * Error0;

值得记住的是，教程注释里特意提醒过一句：变速积分本身没有防止积分饱和的效果，要防饱和还得加积分限幅。笔者后来在速度环里实际用的是固定 KI 加条件积分，本质上是在"代码更简单"和"效果足够"之间做的取舍——学的时候把每种手段的原理看懂，用的时候只带自己验证过的那部分走。

--------------------------------------------------
3.3 惯导与绝对位置控制
--------------------------------------------------

循迹的本质是"跟着线走"：灰度传感器能测到线，但测不到"车在哪里"。一旦场地里有一段没有线的区域，或者要走一条和线无关的路径，循迹就失效了。惯导要解决的正是这个问题——让车不看线也知道自己在哪。

航位推算的原理不复杂，两个信息就够了：走多快，朝哪走。从已知起点出发，把速度按航向方向积分，就是位置。编码器给出轮速，IMU 给出航向，10ms 节拍更新一次位置：

  v = 0.5f * (left_motor_speed_cmps + right_motor_speed_cmps);  /* 平均轮速 = 车体线速度 */
  s_pose.x_cm += v * cosf(yaw_rad) * dt;
  s_pose.y_cm -= v * sinf(yaw_rad) * dt;   /* 注意负号 */

平均轮速能代表车体速度，是差速模型的基础：两个轮子速度相同，车走直线；有差值，车转弯。而航向方向，是这套代码里最容易写错的地方。

坐标约定是这样：世界坐标里，车头朝 +x 时 yaw 为 0；IMU 的 yaw 顺时针为正，范围 0→+180→-180→0，与数学上"逆时针为正"恰好相反。所以车头方向向量不是数学课本上的 (cosθ, sinθ)，而是 (cosθ, -sinθ)——车顺时针转 90 度，方向是 -y，不是 +y。代码注释里特意留了一句提醒："顺时针 yaw：前向 (cosθ, -sinθ)，勿用数学逆时针 (cos,sin)"。这个坑笔者踩过：第一次按 (cos, sin) 写，车绕场地一圈，画出来的轨迹是左右镜像的，当时还以为传感器坏了。

航向还有一个必须处理的问题：环绕。yaw 会从 179 度跳到 -179 度，直接相减会算出 358 度的误差，控制器会以为要转一圈。角误差必须在 ±180 度内处理：

  e = ref_deg - yaw_deg;
  if (e > 180.0f)   { e -= 360.0f; }
  else if (e <= -180.0f) { e += 360.0f; }

另外起点要归零。开始守位之前，先把 IMU 航向重置，让车头对齐世界 +x，再把位置和航向全部清零——如果带上上次遗留的航向偏差，这次积分从一开始就是错的。

有了位置和航向，就能闭环做绝对位置控制。外环是位置环，目标是回家（home 点），状态机分两步走：

  ALIGN_YAW：先把航向转正（yaw 误差进 3 度、出 6 度，滞回防抖）；
  ALIGN_X：  再沿车头方向前后移动（位置误差进 1.5cm、出 3cm）；
  AT_HOME：  判定到位，连续 4 拍（约 200ms）都在死区内，才算成功。

位置误差要先投影到车体坐标系：世界系的偏差 (dx, dy)，乘上航向方向，得到车头方向上的分量，这个分量才是该往前走多少的量。外环算出的目标是"目标速度"，交给内环执行——内环就是 3.1 讲的前馈加弱 PI。

航位推算有一个绕不开的代价：误差会累积。轮子打滑，编码器数了步数但车没动，位置就漂；IMU 有零偏，yaw 慢慢飘，整个坐标系跟着转。所以它只适合短时间、短距离的场合——守位正是这样的场合：起点近、时间短，误差还没攒起来就到目标了。想长时间精准定位，就得再加外部参照（灰度线、视觉、磁条）去修正漂移，那是下一步的事了。

--------------------------------------------------
3.4 参数校准
--------------------------------------------------

调参之前，得先分清两件事：标定，和调参。标定是量出系统的真实值——编码器一圈多少脉冲、轮子半径多大、电机给多少 PWM 能跑多快；调参是调控制效果——KP、KI、前馈系数。标定错了，调参救不回来：编码器一圈脉冲数差一半，速度环算出的速度全是错的，把 PI 调上天也追不上。

先标定几何和符号。编码器每转一圈的脉冲数，要在菜单里"手转一圈"核对（这个工程是 1056）；轮半径是量出来的几何量（直径 48mm，半径 2.4cm），不靠调；再往后是符号对齐——电机指令、编码器读数、位姿积分三处符号必须同相：物理前进，轮速 v>0，yaw 为 0 时 x 增大。哪一处取反，表现就是"车明明往前走，坐标却在后退"，这种错最隐蔽，因为功能看着像好的。

然后是前馈系数。3.1 里说过，FF 是"目标速度需要多少 PWM"的换算。标定方法：给车几个固定的速度指令，记录实际速度对应的 PWM，多点连成一条直线，斜率就是 FF。这个值不必很精确，方向对、量级对就行，剩下的误差 PI 会兜。

接着调速度内环。原则是先内环后外环——内环是执行，外环是规划，执行不准，规划再对也没用。内环是一组参数：KP（35，CCR 每误差）、KI（1.5，每 10ms 积分步进）、积分限幅（400）、输出限幅（2500）、PWM 斜率限制（180）、速度低通滤波（0.35）、误差死区（0.2）。这些参数集中在一个头文件里（vehicle_tune.h），每次改动有据可查。

外环最后调。外环是位置环，KP_X=0.8（cm/s/cm，有 10cm 误差就给 8cm/s 的目标速度）、KP_YAW_V=0.8（cm/s/deg）、最大速度 12cm/s。外环故意放慢：分频到 50ms 才更新一次目标速度，内环仍是 10ms 一个节拍。位置误差再大，速度目标也不突变——外环的"慢"，正是留给内环去"稳"的。滞回死区（位置进 1.5cm 出 3cm、yaw 进 3 度出 6 度）在 3.2 讲过，到位判定是连续 4 拍（约 200ms）都在死区内才算成功，防止刚停又被噪声带出去。

整套代码留了一个开关：POSE_HOLD_USE_FIXED_SPEED，置 1 时外环不算速度、直接给固定 PWM，这是开环调试用的。调参的正确顺序是先开环：确认电机方向、编码器读数、PWM 响应都正确，再切回闭环调 PI。跳过开环直接上闭环，出了偏差你分不清是控制没调好，还是底层符号反了。

IMU 也要标定。上电后静置一段时间（这个工程是 200ms 等稳定，再按 5ms 间隔采 360 个点），取平均算零偏；陀螺仪设一个死区（0.8 度/秒），静止时的微小噪声不积分进航向。惯导的误差全部会累积，标定宁多勿少。

参数从来不是一次调出来的，而是一块一块带着目标试出来的。每调一项，先想清楚"我要观察什么现象、期望它怎么变"再动手。把所有参数集中到一个头文件里，是这套流程能落地的前提——不然调了三天的参数，改没改、改了多少，全凭记忆。

==================================================
四、调试手段
==================================================

--------------------------------------------------
4.1 串口回传
--------------------------------------------------

先想一个问题：调 PID 的时候，怎么知道车现在想干什么？屏幕能显示目标值和实际值，但那是"当前这一瞬间"的数字——你看不到它刚才怎么过来的，也就不知道它是冲过了头又回来，还是慢慢地蹭过去。调参最需要的不是当前值，是趋势。

趋势要靠回传。把数据按固定周期从串口打出来，一行一条，逗号分隔：

  Serial_Printf("%f,%f,%f\r\n", Target, Actual, Out);   /* 目标值,实际值,输出值 */

打印周期和节拍同步（比如 10ms 一条），接收端的时间轴就是均匀的。MCU 上的 printf 要先重定向到串口（重写 fputc），浮点 %f 需要在工程里开启浮点打印支持。

--------------------------------------------------
4.2 上位机曲线
--------------------------------------------------

串口助手看文本看不出趋势，这时候用上位机绘图工具（SerialPlot 这类）。把上面那行数据接进绘图软件，目标值和实际值各画一条线，立刻能看出：实际有没有跟上目标、超调多少、多久稳定、有没有静差。

曲线比数字强的地方，是它同时给出"振幅"和"时间"两个维度：超调是振幅问题，稳定时间和振荡周期是时间问题。数字只能告诉你"现在差多少"，曲线告诉你"是怎么差过来的"。

--------------------------------------------------
4.3 用曲线定位问题
--------------------------------------------------

拿到目标-实际曲线，调参就有据可依：

  · 实际冲过目标又回落（超调大）——减 Kp，或加 Kd 压冲势；
  · 在目标附近来回振荡不收敛——减 Kp，先保证稳定，再谈快；
  · 稳定后和目标差一截（静差）——加 Ki，用积分把最后一截补上；
  · 目标变了但实际跟得慢——加前馈或加 Kp，惯性系统的反应速度取决于这一步。

调参次序也顺理成章：先把曲线调到"不超调、不振荡"，再谈收敛速度，最后用积分消静差。每一步只改一个参数、看一次曲线，不要一次改两个——出了新问题，你分不清是谁干的。

还有一条：只打印当前要观察的那几个量。调内环就打印速度环的量，调外环再换位置环的量。一次全打出来，曲线全是乱的，反而看不清。

==================================================
五、工程习惯
==================================================

前面几章讲的是怎么写代码，这一章讲的是写代码之外、但同样决定成败的习惯。它们不直接产生功能，但没有它们，功能做出来也守不住。

--------------------------------------------------
5.1 备份与版本管理
--------------------------------------------------

备份是最便宜的投资。一份能跑的代码，改坏一次就值回所有备份的工夫。不是为了好看，而是改坏的时候能退回去，而"退回去"这件事，救过笔者的项目不止一次。

--------------------------------------------------
5.2 改动日志与 git
--------------------------------------------------

备份只是把代码存下来，改动日志记录的是"为什么这么改"。每次改动记一行：改了哪里、为什么改、效果如何。看似多花十秒，但三天后再看代码，日志是唯一能告诉你"当时在想什么"的东西。

有条件的项目直接上 git：备份、回退、日志一次全解决，每一步历史都有据可查。习惯和工具是两回事——习惯是"每次改动有据可查"，工具只是实现它的手段。

--------------------------------------------------
5.3 编译自检
--------------------------------------------------

改完代码必须全工程 Rebuild 到 0 Error、确认产物生成，这次改动才算完成。只改不编，等于把错误留到比赛现场才发现。这是笔者固定在规则文件里的一条铁律：禁止只改代码不编译。

--------------------------------------------------
5.4 编码规范与工具
--------------------------------------------------

工程习惯的最后一层，是让规范变成默认值而不是自觉：MISRA-C 代码规范、五层分层架构、UTF-8 统一编码、中文注释规范、先查资料再写控制代码——这些都被笔者固定成规则文件，写代码时直接生效，不需要每次提醒自己。

回头看，这份文档能写出来，本身也依赖这些习惯：代码有注释、参数集中、版本有记录。

6.1 这一年沉淀了什么
--------------------------------------------------

如果用一条主线概括这一年的成长，就是序章里那三层认知从"听说过"变成了"用过"：编程眼界——状态机、时间片、五层架构、函数指针，都是数据结构与代码组织在工程里的落点；数学原理——前馈、PID、航位推算，让微积分第一次有了物理意义；底层实现——时序、中断、寄存器，让程序死机时知道该去翻哪里。

--------------------------------------------------
6.2 下一步：四个方向
--------------------------------------------------

电赛结束不是终点，笔者接下来规划要补的，恰恰是这一年摸到边但没吃透的东西：

  · CAN 总线：多节点通信。四轴四个电调、多个传感器，一条总线解决点对点连线的混乱；
  · DMA：让数据搬运不占 CPU。串口、I2C、ADC 这些反复读写的场景，DMA 是最直接的一层效率提升；
  · FreeRTOS：2.2 末尾说过，时间片轮询的工业级升级。有了手写调度器的底子，FreeRTOS 的任务、队列、信号量都能落到真实代码上理解；
  · 控制算法与仿真：把控制量放进物理模型里先仿真再上实物。仿真能回答"这个参数到底会不会把系统带飞"，比现场试错安全得多。

四个方向的承接关系是清楚的：CAN 和 DMA 补底层实现的深度，FreeRTOS 补编程眼界的上限，仿真补数学原理的验证手段——正好补全三层认知的四个角。
